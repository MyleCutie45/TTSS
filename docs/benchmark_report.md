# Benchmark Report (M4 – Performance Benchmarking)

**Milestone:** M4
**Status:** Final. Benchmark run on 2026-11-19 (Windows: 01:19–08:43, 7 h 24 min; supplementary Linux/WSL2
run: 22 min). Every number in sections 6–8 is measured, unless it is explicitly marked *calculation*,
*estimate* or *hypothesis*.

Sources of all numbers: raw data `results/<experiment>.csv` (one row per run), metadata
`results/<experiment>.meta.json`, tables generated by `scripts/analyze_bench.py` in `results/summary.md`,
memory bandwidth reference `results/membw.txt`, plots in `docs/figures/`. Pilot values (one run per
configuration, `results/pilot*.csv`) were used only to plan the experiments and are not reported as results.

---

## Summary – answers to the five questions

1. **How much faster is the OpenMP version?**
   - With **all four stages parallel** (energy + DP + min + removal), it is **slower** than the sequential
     program in every configuration on the benchmark platform. The speedup is between 0.01 and 0.68.
   - With **the DP kept sequential** (energy + min + removal parallel), it is **1.40–1.79× faster** for
     images of 1920×1080 and larger with 4–16 threads. The best result is 1.79× for 7680×4320 with 8 and
     16 threads. A 512×512 image gains nothing: the speedup is 0.81–1.05.
2. **Which stage gains, which one limits?**
   - **Energy gains most**: 3.3× with 4 threads, up to 3.6× with 8 threads.
   - **Removal** gains only on large images: 1.08× at 1920×1080 (4 threads) and 3.05× at 7680×4320
     (8 threads).
   - **The minimum search** becomes 8–100× slower when it is parallel (1920×1080).
   - **The DP limits the speedup twice:**
     - Parallel, it is 1.8–92× slower than the sequential DP. Every image row needs one OpenMP
       synchronization, and on this platform one synchronization costs 22–167 µs (2–16 threads), while
       one row has only about 2 µs of work.
     - Sequential, it is about 40 % of the run time, so Amdahl's law limits the speedup to about 2.5×.
3. **Variant B vs variant A?**
   - Variant B (one parallel region per seam) is faster with 1–2 threads: 2.2× faster at 1 thread and
     1.6× at 2 threads.
   - The two variants are equal with 4 threads.
   - Variant B is slower with 8–16 threads: 1.2–1.4× slower.
   - Both variants are far slower than the sequential DP on Windows.
4. **Which schedule?**
   - When the DP is sequential, the schedule does not matter: all five schedules are within 5 %, which is
     the size of the run-to-run noise.
   - With the parallel DP:
     - `dynamic` (chunk 1) is 1.4–2.1× slower than `static`.
     - `static,1` is 10–14 % slower than `static`.
     - `guided` and `dynamic,64` are at most 5 % faster than `static`.
   - `static` (the program's default) is a good choice.
5. **Image size and number of seams?**
   - The speedup grows with the image size. With the DP sequential and 4 threads it is 1.03 → 1.44 → 1.61
     → 1.72 from 512×512 to 7680×4320.
   - The number of removed seams (10/20/30 % of the width) hardly changes the speedup.

**Supplementary result:** the same code, compiled for Linux and run in WSL2 on the same laptop.
- With 2–4 threads the extra time per DP row is −0.4 to +0.1 µs, instead of 22–45 µs on Windows.
- The parallel DP is about as fast as the sequential DP (variant A, 0.96× with 4 threads) or faster
  (variant B, up to 1.27×).
- The version with all four stages parallel reaches 1.36× (1920×1080) to 1.71× (7680×4320) with 4 threads. **The slow parallel DP is therefore caused by the OpenMP runtime on Windows, not by
the algorithm.**

## 3. Benchmark Images

Created by `scripts/make_bench_images.py` (list with hashes: `bench_images/manifest.json`).

- **Source photos.** The full-resolution source photos (`images/SOURCES.md`) are not available on the benchmark
  machine, and Unsplash blocks automated downloads. The **800-pixel PNG copies in `tests/data/`** were used as
  sources: center crop to the aspect ratio, then Lanczos resampling.
- **Main series** (`person_desert`): 512×512 (scale 0.96), 1920×1080 (×2.4), 3840×2160 (×4.8) and 7680×4320
  (×9.6). **The three large images are strongly upscaled** (smoother than real photos).
- **Content check** (1920×1080): the other four photos (×2.4 / ×3.6) and seeded random noise.
- **Why upscaling is acceptable for timing.** Every stage loops over all `W × H` pixels of the current image
  with no content-dependent work. The only exception is the length of the row part that the removal shifts,
  which depends on the seam position. So the run time should depend on the size, not on the content. The
  `content` experiment confirms this with measurements (section 6.7).

## 4. Methodology

| Rule | Implementation |
| ---- | -------------- |
| Only the algorithm is timed | The program measures `carve()` with `std::chrono::steady_clock` (columns `t_energy`, `t_dp`, `t_min`, `t_backtrack`, `t_removal`, `t_total`). Loading and saving the image are outside the measurement |
| Same work in seq and omp | Same binary, same input, same target width. Every output image is hashed (SHA-256) and compared with the sequential output of the same experiment; a run with a different output would be flagged (`hash_ok = 0`) |
| `T_seq` | Median of `--mode seq` (the real sequential code), **not** OpenMP with 1 thread. Speedups always compare runs of the same experiment (same session, same platform) |
| Repetitions | 1 warm-up round (not used) + 5 measured rounds, except where stated in section 5 |
| Order | Inside every round the configurations run in a shuffled order (fixed seed 2026). The sequential configurations run first in each round, so the reference hash exists |
| Statistics | Median of the measured runs. Variability = min, max and interquartile range (IQR = Q3 − Q1, shown as % of the median) |
| Speedup / efficiency | `S(p) = T_seq / T_omp(p)`, `E(p) = S(p) / p`, both from medians. Stage speedup = `t_stage(seq) / t_stage(omp)` |
| Oversubscription | 16 threads on 8 logical processors is marked "(over)" in every table and shaded in every plot |
| Initialization vs steady state | Every run is a new process. `t_total` includes the creation of the OpenMP thread pool and the one-time work (copy of the input, gray conversion, final crop). The one-time work is measured directly as `t_total − Σ stage times` and compared with two regression models (section 6.8) |
| Memory bandwidth reference | `scripts/membw.cpp`: read / write / copy of 512 MB arrays with 1–8 threads, best of 5 (section 6.10) |
| Raw data | Every run is one row in `results/<experiment>.csv`. Tables and plots are generated by `scripts/analyze_bench.py` |

## 5. Experiments and Deviations from the Plan

| Experiment | Configurations | Rounds |
| ---------- | -------------- | ------ |
| `main_nodp` | 4 sizes × 3 reductions (10/20/30 % of the width) × {seq, omp 1/2/4/8/16 threads}; parallel stages energy + min + removal (DP sequential) | 1 + 5 |
| `main` | Same grid, **all four stages parallel** (energy + DP variant A + min + removal); 7680×4320 only at −10 % | 0 + 3 |
| `stages` | 1920×1080, −20 %: seq; omp with none / only energy / only DP (A) / only DP (B) / only min / only removal / energy+min+removal / all (A) / all (B); 1/2/4/8/16 threads | 1 + 5 |
| `schedule` | 1920×1080, −20 %: `OMP_SCHEDULE` = static, static,1, dynamic, dynamic,64, guided; 2/4/8 threads; energy+min+removal and all stages | 0 + 3 |
| `content` | 1920×1080, −20 %: 6 different images, seq and omp 4 threads (energy+min+removal) | 1 + 5 |
| `wsl` (supplementary) | Linux build in WSL2. 1920×1080, −20 %: seq; omp 1/2/4/8 threads × {only DP (A), only DP (B), energy+min+removal, all (A)}. 3840×2160 and 7680×4320, −10 %: seq; omp 4 threads {energy+min+removal, all (A)} | 1 + 5 |
| `membw` (supplementary) | Memory bandwidth reference, 1/2/4/8 threads | 2 runs, best of 5 each |

**Why fewer runs than planned for `main` and `schedule`.**
- The pilot (planning data, one run each) showed that the parallel DP costs about 12 µs (1 thread) to
  118 µs (16 threads) of synchronization per image row, while the sequential DP needs about 2 µs of work per
  row.
- With all stages parallel, the complete grid with 1 + 5 rounds was *estimated* at about 22 hours.
- The user chose an overnight plan (*estimate* 8–9 hours): `main` with 3 measured rounds and the 7680×4320
  image only at −10 %, and `schedule` with 3 rounds.
- The warm-up round is skipped for these two experiments because every run is a new process and the preceding
  experiments keep the machine at operating temperature.

**Why `main_nodp` was added.** M4.md asks for the "combined" OpenMP version. With the DP stage parallel, the
combined version is slower than the sequential program (pilot). So a second combined version, with every stage
parallel except the DP, is measured on the full grid as well. Both are reported.

**Other deviations.**
- **DP variant A vs B.** The plan proposed all sizes with 8 and 16 threads. Measured: 1920×1080 with all
  thread counts 1–16 (`stages`), plus variant A at all sizes inside `main`. One parallel-DP run at 4K/8K
  takes 1.5–7 minutes, and the per-row synchronization cost does not depend on the image size (section 7.1).
- **`OMP_PLACES` / `OMP_PROC_BIND`** (benchmark_plan §6) were not varied; they were left unset. Not tested.
- **The hybrid P/E hypothesis** cannot be tested: the benchmark laptop is not the M0 development machine
  (i9-13900H) and has 4 equal cores.
- **Added:** `wsl`, to test the platform hypothesis of `parallelization_strategy.md` §11.4, and `membw`, as a
  reference for the memory-bandwidth analysis.

## 6. Results

### 6.1 Data quality

- **Runs.** 1191 runs in total: 1053 on Windows and 138 in WSL2.
  - 153 warm-up runs were not used.
  - **0 runs failed** (exit code ≠ 0 or timeout).
  - **0 runs produced a wrong output.** Every OpenMP output image was byte-identical to the sequential output
    of the same experiment, for every stage combination, thread count, schedule and image.
- **Variability.** IQR < 5 % of the median for 92.6 % of the 244 configurations.
  - The largest IQR in the Windows experiments is 9.7 % (512×512 −30 % seq, n = 3, run time 0.09 s).
  - WSL2 is noisier: up to 12 % with 4 threads and 39 % with 8 threads.
- **One clearly disturbed run.** 7680×4320 −10 % seq, `main_nodp` round 3 (04:04): 90.1 s, while the other
  rounds took 70.4–71.2 s. The cause is unknown. The median (70.74 s) is not affected.

### 6.8 Fixed part vs per-seam work (sequential runs of `main` + `main_nodp`)

Seam number k (k = 0, 1, …) is computed on an image of width W − k. So **the cost of one seam shrinks during a
run**, and the total work of a run is P = H · (s·W − s(s−1)/2) "pixel visits". Three ways to find the fixed
part (the work that does not depend on the seams):

| Size | Measured directly: `t_total − Σ stages` (median) | Model 1 `t = a + c·P`: a | Model 2 (naive) `t = a′ + b·s`: a′ | a′ as % of `t_total` at −10 % |
| ---- | ------------------------------------------------- | ------------------------ | ---------------------------------- | ----------------------------- |
| 512×512 | 0.0014 s | 0.0006 s | 0.0064 s | 19 % |
| 1920×1080 | 0.0052 s | −0.0134 s | 0.1692 s | 17 % |
| 3840×2160 | 0.0162 s | 0.3008 s | 1.7665 s | 21 % |
| 7680×4320 | 0.0583 s | 2.0210 s | 14.0960 s | 20 % |

8 % faster at 7680×4320. So compare speedups, not absolute times, across platforms.

## 7. Analysis

### 7.1 Synchronization: why the parallel DP is so slow on Windows

**What the DP has to do.**
- Row y of the cumulative-energy matrix `M` needs the complete row y − 1. So the rows are processed one after
  another, and only the cells of one row can be split among the threads (`parallelization_strategy.md` §4).
- After every row all threads must wait until the whole row is finished. This is a **barrier**: a point where
  every thread waits until all threads have arrived.
- **Variant A** starts a new parallel region for every row: the threads are woken up ("fork") and wait for
  each other at the end ("join" = barrier).
- **Variant B** starts one region per seam and has one barrier per row (the implicit barrier of `omp for`).
- At 1920×1080 with 384 seams that is **414 336 synchronizations per run**.

**Measured cost (section 6.5).**
- One DP row needs 1.84 µs of real work: about 1.06 ns per cell (*calculation*), at an average width of
  1728 pixels during the run.
- On Windows, every row costs **+9.2 µs with 1 thread** in variant A. This is the cost of entering and leaving
  a parallel region, even without other threads. It agrees with the 8 µs measured by the M2 micro-benchmark on
  another machine (`parallelization_strategy.md` §11.4).
- With 2–16 threads the extra cost is **22–167 µs per row**, and it grows with the number of threads.
- With 4 threads that is 414 336 × 45 µs ≈ 18.8 s of waiting (*calculation*), compared with 0.76 s of real DP
  work. This matches the measured `t_dp` of 19.6 s.

**A simple model** (*calculation* from the measured values).
- Time per row ≈ work per row / p + o(p), where o(p) is the synchronization cost per row.
- The parallel DP is faster than the sequential DP only if the work saved per row, w·W·(1 − 1/p), is larger
  than o(p). Here w ≈ 1.06 ns per cell on Windows and 1.12 ns under Linux.
- **Windows:** o(4) ≈ 45 µs, so the image would have to be wider than about **56 000 pixels**. No real image is
  that wide.
- **Linux:** o(4) ≈ 1.0 µs (variant B) and 1.5 µs (variant A), estimated from 1.53 / 2.01 µs per row minus
  1.94/4 µs of work. The break-even width is about 1 200 (B) and 1 800 (A) pixels.
- This matches the Linux measurements:
  - At 1920×1080 (average width 1728), variant B is faster than the sequential DP (1.27×) and variant A
    roughly equal (0.96×).
  - At 3840 and 7680 pixels the parallel DP is clearly faster (1.26× and 1.50×).
- The model is only a first approximation: at 7680×4320 it predicts more speedup than measured.

**Why it is so slow on Windows.**
- The `wsl` experiment ran the same code on the same CPU. With 2–4 threads the extra time per DP row is
  22–45 µs on Windows and −0.4…+0.1 µs under Linux.
- So **the cost does not come from the algorithm or the hardware. It comes from the OpenMP runtime on
  Windows.** This confirms the hypothesis of `parallelization_strategy.md` §11.4 with a measurement.
- *Hypothesis* (based on how the GCC OpenMP runtime is built; not verified with a profiler):
  - On Linux, libgomp lets a waiting thread spin (check a variable in a loop) for a short time, and then
    sleep on a *futex*, a very cheap operating-system mechanism.
  - The Windows (MinGW) build of libgomp uses a generic implementation based on mutexes and semaphores. A
    waiting thread therefore sleeps in the operating system and has to be woken up by another thread through
    a system call. That costs tens of microseconds, and the threads are woken one after another, so the cost
    grows with the number of threads.
  - This would also explain why `OMP_WAIT_POLICY=active` had no effect in M2.

**Variant A vs B.**
- Variant B avoids one fork per row and is clearly better with 1–2 threads (3.35 vs 11.01 µs per row at
  1 thread).
- With 8–16 threads it is worse (86.9 vs 73.6 µs at 8 threads). We have no measured explanation for this
  crossover.
- *Hypothesis:* in variant B every thread must enter the shared bookkeeping of the `omp for` loop for every
  row, and on Windows the contention for that structure becomes expensive with many threads. In variant A the
  master thread prepares the loop before the team starts.
- Under Linux variant B is better at every thread count measured.

**Oversubscription and full machine.**
- On Windows, 16 threads make the parallel DP 1.6–1.9× slower than 8 threads: 1.6–1.7× in `main` (all stages,
  variant A) and 1.9× for variant B alone. There are more threads to synchronize per row.
- Under Linux, 8 threads (all logical CPUs busy) are already worse than 4 (DP A: 4.55 vs 2.01 µs per row) and
  very noisy (IQR up to 39 %). At a barrier all threads wait for the last one, and when any other activity
  interrupts one thread, all threads wait.

### 7.2 Sequential bottleneck and Amdahl's law

**The limit.**
- Amdahl's law: if a fraction f of the run time is parallel, the speedup with p threads is at most
  1 / ((1 − f) + f/p). Even with infinitely many threads it cannot exceed 1 / (1 − f).
- For energy+min+removal at 1920×1080, f = 0.596 (from the sequential stage times). The remaining 40 % are
  mainly the sequential DP (39 %) and the backtracking.

| Threads p | Amdahl limit S(p) | Measured S(p) | Measured / limit |
| --------- | ----------------- | ------------- | ---------------- |
| 2 | 1.42 | 1.28 | 90 % |
| 4 | 1.81 | 1.52 | 84 % |
| 8 | 2.09 | 1.48 | 71 % |
| 16 (over) | 2.27 | 1.47 | 65 % |
| ∞ | 2.48 | – | – |

**Where the gap comes from** (measured, section 6.4):
- Energy reaches 3.3×, not 4×, with 4 threads.
- Removal reaches only 1.11× at this size, and the minimum search becomes slower (7.3).
- 8 threads share 4 physical cores (7.5).
- **The sequential DP becomes about 5 % slower** inside the parallel program (stage speedup 0.95–0.96 with
  4–16 threads at every size ≥ 1920×1080). *Hypothesis:* the clock frequency is lower after the parallel stages
  have heated the chip (laptop power and temperature limits). The frequency was not recorded.

**Consequence.** Without a faster DP this version can never exceed about 2.5×. More threads cannot change
that. On Windows the DP cannot be parallelized profitably (7.1). Under Linux, the parallel DP lifts the
4-thread speedup at 7680×4320 from 1.52× (DP sequential) to 1.71×.

**The sequential outer loop.**
- Seam i + 1 needs the image after seam i, so the seams are always computed one after another.
- The parallel regions are therefore entered again for every seam: 3 regions per seam for energy+min+removal,
  that is 1 152 regions per run at 1920×1080.
- Their start-up cost is paid every time (7.3).

### 7.3 Start-up cost of a parallel region and small work

**The minimum search.**
- It scans one row of 1920 values per seam: 3.4 µs of sequential work.
- As a parallel region it costs about 28 µs (1 thread) to about 320 µs (4–16 threads) per seam.
- Result: 8–100× slower. **It should stay sequential.**

**Small images.**
- At 512×512 one removal has about 20 µs of work per seam. Parallel removal is 4× slower (0.26).
- One energy computation has about 0.34 ms of work per seam. Energy reaches only 1.99× with 4 threads, against
  3.27× at 7680×4320.
- At 7680×4320 the work per region is 41 ms (energy) and 14 ms (removal), so the start-up cost no longer
  matters. Removal then reaches 2.8–3.1× (section 6.4).

**A region costs more when the threads were idle longer before it** (4 threads, 1920×1080). Stage times are
measured. The idle gap is a *calculation* from the sequential stage times per seam.

| Stage | Inside energy+min+removal | Only this stage parallel | Difference per region |
| ----- | ------------------------- | ------------------------ | --------------------- |
| energy | 0.311 s (follows the parallel removal directly) | 0.386 s (≈ 2.4 ms idle before) | ≈ 195 µs |
| removal | 0.126 s (≈ 0.07 ms after the parallel min) | 0.200 s (≈ 4.7 ms idle before) | ≈ 193 µs |
| min | 0.047 s (≈ 2 ms after the parallel energy) | 0.122 s (≈ 5.1 ms idle before) | ≈ 197 µs |

- In all three cases, the configuration with the longer idle gap costs about 0.075 s more per run, that is
  about 195 µs per region.
- *Hypothesis:* while the threads have no work, they and their cores go to sleep, and a longer pause lets them
  sleep more deeply. Waking them up then takes longer. Not verified with a profiler.

### 7.4 Memory bandwidth and caches

**Sequential program: energy and DP are compute-bound.**
- Their time per pixel visit is the same whether the working set fits in the L3 cache (512×512, 3.1 MB) or
  only in RAM (7680×4320, 398 MB): energy 1.43 → 1.38 ns, DP 1.02 → 1.02 ns (section 6.8). They are limited by
  computation, not by memory.
- *Calculation:* energy writes 4 bytes per pixel visit in 1.4 ns, that is 2.9 GB/s. This is far below the
  14.5 GB/s that one thread can write (section 6.10).

**Sequential program: removal is memory-bound.**
- Its time per pixel visit grows 6.5× from 512×512 (data in the cache: 0.074 ns) to 7680×4320 (data in RAM:
  0.481 ns). It shifts the image with `memmove`, which does almost no arithmetic.

**Parallel energy.**
- At 1920×1080 with 4 threads, energy writes 2.87 GB in 0.311 s, that is 9.2 GB/s (*calculation*: 716.8 M
  pixel visits × 4 B). This is about 55 % of the measured write limit of about 17 GB/s.
- At 7680×4320 with 8 threads it writes 10.4 GB/s (about 61 %).
- So the energy stage does not hit the bandwidth limit. Its plateau between 4 and 8 threads comes from the 4
  physical cores (7.5).

**Parallel removal at 7680×4320.**
- *Estimate*, with the assumption that on average half of each row is shifted (seam positions were not
  recorded): removal moves 4 bytes per pixel visit (2 B read + 2 B written).
- With 8 threads that is 4 B / 0.156 ns ≈ 26 GB/s, the same as the measured copy bandwidth (24–25 GB/s).
- **So with 8 threads removal works at the memory bandwidth limit, and more threads cannot help.** With 1
  thread the same estimate gives about 8 GB/s.

**Conclusion.** "Removal flattens because of memory bandwidth" is true for large images. For images of
1920×1080 and smaller, the start-up cost of the parallel region limits the removal much earlier (7.3).

### 7.5 Hyper-Threading and oversubscription

**Hyper-Threading** (two logical processors share one physical core and its execution units):
- 8 threads vs 4 threads gives +2–3 % for the whole run (energy+min+removal, ≥ 1920×1080).
- For the energy stage at 7680×4320 it gives +10 % (3.27 → 3.59).
- The two threads of one core compete for the same execution units, so the useful parallelism of this laptop
  is about 4.

**Oversubscription (16 threads on 8 logical processors):**
- With the DP sequential, it is as fast as 8 threads for ≥ 1920×1080 (difference ≤ 2 %, within the noise),
  and slower for 512×512 (0.86 vs 0.94).
- With the parallel DP it is 1.6–1.7× slower than 8 threads (7.1).

### 7.6 Scheduling

**Energy, min and removal.**
- Every row has the same amount of work, so a static distribution is already balanced.
- All five schedules are within 2.6–4.6 % of each other, about the size of the noise. Even `dynamic` with chunk
  1 is harmless here: a loop has only 1 080 rows of about 1 µs each.

**The DP column loop is very sensitive** (about 1 700 iterations of about 1 ns per row):
- **`dynamic` (chunk 1)** takes every single column from a shared counter. That is 716 M counter updates per
  run, and the counter's cache line moves between the cores.
  - Result: 34.5 s instead of 16.5 s with 2 threads.
  - *Calculation:* (34.527 − 16.477) s / 716.8 M ≈ 25 ns per iteration.
- **`static,1`** gives column x to thread x mod p, so neighbouring columns of `M` are written by different
  threads. One 64-byte cache line holds 16 columns, so several cores write the same line at the same time.
  This is called **false sharing**: the line must move between the cores although no value is really shared.
  - Result: 10–14 % slower than `static`.
- **`dynamic,64` and `guided`** are 5 % faster than `static` with 2 threads, about equal with 4, and 3–4 %
  slower with 8.
  - *Hypothesis:* the imbalance in the DP is not in the work but in the different wake-up times of the threads
    after each barrier. With dynamic chunks, threads that are awake earlier take more chunks.

**Conclusion.** Keep `static`. Avoid `dynamic` with small chunks and `static,1` for loops over the columns of a
row.

### 7.7 Image size and number of seams

**Size: the speedup grows with the image.**
- DP sequential, 4 threads: 1.03 → 1.44 → 1.61 → 1.72.
- All stages, 4 threads: 0.03 → 0.10 → 0.19 → 0.39 (7680×4320 at −10 %).
- The work per parallel region grows with W·H (energy, removal) or with W (one DP row), while the start-up
  and synchronization cost per region or row stays the same. So the ratio work / overhead improves with size.

**Seams: the number of seams hardly changes the speedup** (1.62 / 1.61 / 1.61 at 3840×2160).
- Every seam has the same structure, and the width shrinks by at most 30 % during a run.
- More seams simply repeat the same per-seam pattern more often.

### 7.8 Initialization vs steady state

**The fixed part of a run is very small** (section 6.8).
- It consists of the copy of the input, the gray conversion and the final crop.
- Measured directly as `t_total − Σ stages`, it is 1.4 ms (512×512) to 58 ms (7680×4320). That is ≤ 0.5 % of
  the run time for 1920×1080 and larger, and 1.5–4 % for 512×512.
- Almost all of the time is steady-state, per-seam work.

**A lesson about models.**
- The naive regression `t = a′ + b·s` would claim a fixed part of 17–21 % of the run (e.g. 14.1 s at
  7680×4320). That is wrong.
- The cost of one seam is not constant: it shrinks with the width. A straight line through the three
  reductions therefore cuts the time axis above zero.
- Model 1 uses the correct amount of work P and comes much closer: about 0 s at 512×512 and 1920×1080. It
  still gives 0.3 s and 2.0 s for the large images, because the cost per pixel visit itself changes by 1–2 %
  between the reductions (e.g. 2.92 → 2.87 ns at 7680×4320).
- **An intercept is an extrapolation, not a measurement.**

**Thread-pool creation.**
- It happens once per run, in the first parallel region, and is included in that stage's time. It cannot be
  separated with per-run timing.
- Measured upper bound: at 512×512 (−10 %) the run with 16 threads takes only 6 ms longer than the run with
  1 thread (0.042 vs 0.036 s). That difference contains the creation of 15 threads plus all 153 parallel
  regions of the run. So the thread creation costs less than 6 ms, which is negligible for every image size.

### 7.9 Image content

- Six images, including random noise, give sequential times within 4.4 % and speedups of 1.43–1.54
  (section 6.7). That is within the measurement noise.
- So the run time does not depend on the content, and the upscaled benchmark images give representative
  timings (section 3).

### 7.10 Consequences for M5 (suggestions, not measured)

- On this platform keep the DP sequential, or replace the per-row barrier with a scheme that synchronizes less
  often, e.g. blocks of rows with overlapping "triangles". This is an algorithmic change and would need new
  correctness tests (M3).
- Another option is an OpenMP runtime with cheaper barriers: the Linux results show what is possible.
- Keep the minimum search sequential.
- Use parallel removal (and energy) only above a size threshold, e.g. with an OpenMP `if` clause.
- Merge energy, min and removal into one parallel region per seam, so the threads are woken up once instead
  of three times per seam (7.3).

## 9. Limitations

- **One machine and one compiler for the main results**, with one OpenMP runtime (libgomp on Windows). The
  synchronization cost measured here is specific to this platform (section 7.1).
- **WSL2 is a virtual machine,** and it uses another compiler version (GCC 15.2 vs 16.2) and another OpenCV
  version (only I/O and the gray conversion).
  - Its runs are noisier (IQR up to 39 % with 8 threads).
  - Its energy stage scales less well (2.35× vs 3.31× with 4 threads at 1920×1080; cause not investigated).
  - Use it to compare speedups and the DP overhead, not absolute times.
- **The laptop's clock frequency depends on temperature and power limits** (turbo) and was not recorded.
  Effects that may come from it are marked as hypotheses. Mitigations: AC power, Best performance, shuffled
  order, medians, reported variability.
- **The large images are upscaled** from 800-pixel sources (section 3). The content experiment shows that this
  does not change the timing.
- **Fewer repetitions in two experiments.** `main` and `schedule` have 3 measured runs per configuration
  instead of 5.
- **No hardware performance counters** (cache misses, memory traffic per stage). Bandwidths per stage are
  calculated from byte counts; for removal they rest on an assumption about the seam positions (section 7.4).
- **Not tested:** `OMP_PLACES` / `OMP_PROC_BIND`, and DP variant B at sizes other than 1920×1080.
